# Prometheus Replacement example
This example contains files to allow a user to replace an installation of kube-prometheus-stack. The opentelemetry-kube-stack chart aims to make the replacement process straightforward by utilizing the target allocator to pull any servicemonitors and podmonitors.

This example requires cert-manager to be installed because the target allocator is configured with `mtls.enabled: true` and `mtls.useCertManager: true`. The kube-apiserver, kube-controller-manager, and kube-scheduler ServiceMonitor endpoints require authentication by default, so their ServiceMonitors reference a bearer-token Secret. This credential must be supplied by the target allocator to collectors securely using mTLS. CoreDNS, kube-dns, kube-etcd, and kube-proxy do not reference this Secret by default because their default metrics endpoints do not use bearer-token authentication. If you don't have cert-manager installed, then you can [provide your own certificates](https://github.com/open-telemetry/opentelemetry-operator/blob/main/docs/target-allocator/README.md#without-cert-manager-user-provided-certificates). If mTLS is disabled and `allowInsecureAuthSecrets` remains false, the collectors will run but receive 401 errors from the authenticated endpoints. kube-prometheus-stack doesn't have this mTLS requirement because the target allocator and collector architecture is specific to OpenTelemetry.

> [!INFO]
> This chart has most of the same configurations as the kube-prometheus-stack chart, but requires that kubelet monitoring is done via a manual scrape config. This is because of how the prometheus-operator manages endpoints for the Kubelet service. If you'd like to avoid a scrape-config altogether, it's recommended to use the kubelet receiver in the opentelemetry collector.
